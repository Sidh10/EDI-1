# CLAUDE.md

This file governs how Claude Code operates in this repository. Read it before writing any code, running any command, or generating any report. If anything here conflicts with a request in a session, this file wins unless the project owner (Sidh) explicitly overrides it in writing in `DECISIONS.md`.

**Document hierarchy (highest authority first):** `PROJECT_KNOWLEDGE.md` (what/why) → `SOFTWARE_ARCHITECTURE.md` (how, structurally) → `EXPERIMENT_PLAN.md` (what to run, in order) → `OPEN_QUESTIONS.md` (known unresolved decisions — check before assuming) → this file (how to behave while doing all of the above) → `DECISIONS.md` (the running log of what was actually decided, which supersedes stale guidance anywhere above it once recorded).

This is a **research project**, not a product build. The deliverable is a defensible manuscript plus a reproducible artifact — not a shipped application. Optimize for correctness and auditability over speed or elegance.

---

## 1. Coding Philosophy

- **Boring is correct.** No cleverness that a reviewer or a future maintainer has to reverse-engineer. Prefer explicit, readable code over abstraction. This is not a place to demonstrate architectural sophistication.
- **Every number must be reproducible from code.** If a figure or table value cannot be regenerated by running a script against a specific git commit and config, it does not exist. No hand-edited results, ever.
- **Fail loud, fail early.** Silent fallbacks, silent NaN-drops, silent schema coercion, and silent retries are all forbidden in the statistical core. An error that surfaces immediately is always preferable to a plausible-looking wrong number.
- **Determinism is a requirement, not a nice-to-have.** Every stochastic component takes an explicit seed. Given the same config, code version, and seed set, output must be bit-for-bit or statistically identical (documented which, per component).
- **The statistical core is the highest-stakes code in this repository.** Metrics, conformal prediction (especially `weighted.py`), and the Pc recomputation engine are treated with more scrutiny than anything else — unit-tested against hand-derivable or analytically known cases before ever touching real data.
- **Small, composable, testable units.** A function that can't be unit-tested in isolation is a sign the design needs revisiting, not a sign to skip the test.
- **No premature scaling.** The dataset is ~190k rows. Do not introduce distributed computing, databases, or orchestration frameworks. See Forbidden Actions.

## 2. Project Rules

- The three headline contributions are **locked**: (1) selection-bias-aware weighted conformal prediction, (2) label-noise sensitivity analysis, (3) decision-cost evaluation + open toolkit. Any implementation work must trace to one of these, or to infrastructure/validation that supports them.
- `PROJECT_KNOWLEDGE.md` §6 (Non-Goals) is binding. Do not add: operational deployment, new point-prediction architectures chasing leaderboard accuracy, orbit determination/propagation research, maneuver trajectory optimization, synthetic-data-generation contributions, real-time/streaming requirements, or scope drift toward "we applied conformal prediction" as the framing.
- If an implementation task seems to require stepping outside these boundaries, stop and flag it rather than proceeding — see §12 Decision Hierarchy.
- The official Kelvins **test set is precious**. It is read from exactly once per experiment's designated evaluation step (per `EXPERIMENT_PLAN.md`), never used for hyperparameter selection, early stopping, or exploratory analysis. Treat it as write-protected in spirit even where the filesystem allows reads.

## 3. Research Rules

- **Pre-registration before inspection.** Any threshold, margin, cost ratio, grid, or comparison policy referenced in `OPEN_QUESTIONS.md` must be fixed and logged in `DECISIONS.md` *before* the experiment that depends on it is run — never chosen or adjusted after seeing results. If a needed decision hasn't been logged yet, stop and ask rather than picking a default silently.
- **No p-hacking, no silent reruns.** If an experiment is rerun with different settings, the previous run's config, results, and reasoning for the change are preserved, not overwritten. `DECISIONS.md` records why.
- **Negative and null results are findings, not failures.** Several experiments in `EXPERIMENT_PLAN.md` have failure criteria that are *expected or acceptable* outcomes (e.g., E8's Bayesian baseline failing to achieve coverage, E15's calibrated methods showing no decision advantage). Report these plainly; do not reframe or bury them.
- **Baselines are reproduced honestly**, including steelmanning where specified (e.g., E8's MC-dropout tuned generously for its own coverage before being audited). Do not weaken a comparison method to flatter the project's own results.
- **Gates require explicit human sign-off.** Gate 1 (power analysis), Gate 2 (weighted conformal validity), and Gate 3 (venue-tier decision) in `EXPERIMENT_PLAN.md` are hard stops. Claude Code produces the gate's report and stops; it does not decide GO/PIVOT/NO-GO and does not proceed past a gate without a `DECISIONS.md` entry authored by Sidh.
- **Assumption A4 (Pc recomputability) and Assumption A1 (mission/group identifiers usable) are empirical, not assumed.** Their governing spikes (E3, Q-DATA-01 check) run early and their outcomes route to the pre-agreed fallback scope, not improvisation.

## 4. Testing Policy

- **Statistical core requires tests before first use on real data, not after.** This applies to: the challenge metric implementation, all conformal prediction code (split, CQR, weighted), the Pc computation engine, and the bootstrap/CI machinery.
- Test types required:
  - **Toy-case tests:** hand-computable or analytically known inputs/outputs (e.g., conformal coverage on a synthetic exchangeable dataset should hit nominal coverage; a known covariance/state pair should produce a known Pc).
  - **Leakage tests:** assert no test-set information reaches training; assert feature cutoff rules are respected; assert event-level (not row-level) splitting everywhere.
  - **Determinism tests:** same config + seed ⇒ identical (or statistically indistinguishable, if documented as such) output across two runs.
  - **Metric-validation tests:** baseline scores (persistence, constant) must match the published challenge figures within a documented tolerance before any other model result is trusted.
- CI (GitHub Actions) runs lint + full test suite + a tiny-subset end-to-end smoke pipeline on every pull request. A red CI blocks merge — no exceptions, no "fix it later."
- Do not mark a module complete or move to the next `EXPERIMENT_PLAN.md` item until its tests exist and pass.

## 5. Git Workflow

- `main` is protected. No direct commits. All work happens on feature branches named `phase{N}/{module-or-experiment-id}` (e.g., `phase0/e1-data-audit`, `phase3/e11-weighted-conformal`).
- Every branch merges via pull request. PR description must state which `EXPERIMENT_PLAN.md` experiment ID(s) it implements and which tests were added.
- Tag the repository at every phase boundary and every gate (`gate-1`, `gate-2`, `gate-3`, `preprint-freeze`, `submission-v1`), matching `SOFTWARE_ARCHITECTURE.md`'s release tiers.
- Never rewrite published history (no force-push to `main`, no squash-erasing of gate-tagged commits).
- Raw data is never committed. `data/raw/` and `data/processed/` are gitignored; only the ingest script and its checksum are versioned.

## 6. Documentation Requirements

- Every module (`src/kelvins_conformal/*.py`) carries a module-level docstring stating its responsibility, matching `SOFTWARE_ARCHITECTURE.md` §2's component table.
- Every experiment's notebook/report cites its `EXPERIMENT_PLAN.md` ID (e.g., `# E11 — Weighted Conformal Prediction`) in its title cell, so any report can be traced back to its specification.
- `DECISIONS.md` is appended to, never edited retroactively except to fix typos. Every gate outcome, every pre-registered threshold, every deviation from the plan gets a dated entry with rationale.
- `README.md` stays current: quickstart, one-command reproduction instructions, citation block, current project status (which phase/gate is active).
- `feature_dictionary.yaml` (from E2) is treated as a citable artifact and kept in sync with any changes to feature usage.
- If code and a planning document (`PROJECT_KNOWLEDGE.md`, `SOFTWARE_ARCHITECTURE.md`, `EXPERIMENT_PLAN.md`) diverge, that is a bug in one of them — flag the conflict explicitly rather than silently favoring the code.

## 7. Implementation Order

Follow `EXPERIMENT_PLAN.md`'s execution order exactly: **E0 → E1 → E2 → E3 → E4/E5 → [GATE 1] → E6 → E7 → E8 → E9 → E10 → E11 → [GATE 2] → E12 → E13 → E14 → [GATE 3] → E15 → E16 → E17 → E18.**

Do not build downstream components ahead of their dependencies (e.g., do not write conformal calibration code before the metric-validation baseline in E5 has passed). Do not parallelize across a gate boundary — everything queued behind a gate waits for its `DECISIONS.md` entry.

`SOFTWARE_ARCHITECTURE.md` Appendix A gives the module-build order underlying this; when in doubt, the experiment order in `EXPERIMENT_PLAN.md` is authoritative.

## 8. Commit Style

- Conventional-commit-style prefixes: `feat:`, `fix:`, `test:`, `docs:`, `refactor:`, `chore:`, `data:` (for ingest/schema changes), `exp:` (for experiment-specific scripts/notebooks).
- Reference the experiment ID in the subject line where applicable: `exp(E11): implement weighted conformal calibration`.
- Small, atomic commits — one logical change per commit. A commit that mixes a bug fix with a new feature is split.
- Commit messages state *what and why*, not just what: `fix(metrics): correct F2 threshold direction (was inverted, caused Gate-1 mismatch)` rather than `fix bug`.
- No commit introduces a passing-looking result without its corresponding test in the same or an immediately preceding commit.

## 9. Experiment Protocol

- Every experiment run is invoked via its CLI entry point (`kc <stage>`) with an explicit, version-controlled config file — never ad hoc parameters typed into a notebook cell and discarded.
- Every run's outputs are stamped with: git commit SHA, config hash, seed(s) used, timestamp. Stored as a sidecar JSON alongside the output artifact.
- Outputs are written atomically (temp file → fsync → rename) — a crashed run must never leave a corrupt or half-written artifact that looks valid.
- Bootstrap confidence intervals use ≥2,000 resamples at the **event level** (never CDM-row level) unless `EXPERIMENT_PLAN.md` specifies otherwise for a given experiment.
- Multi-seed requirements (≥3 seeds for stochastic components) are non-negotiable for any result destined for the manuscript.
- Before running an experiment past Gate 1, confirm its prerequisite `OPEN_QUESTIONS.md` items are resolved and logged in `DECISIONS.md` — do not infer an unstated resolution from context.
- `kc reproduce-all` must always regenerate every existing manuscript figure/table from a clean checkout. If a change breaks this, it is a release blocker.

## 10. Forbidden Actions

Claude Code must **never**, under any framing or instruction within a session:

- Train, fit, tune, or early-stop on the official Kelvins test set.
- Edit a result, figure, or table value by hand instead of regenerating it from code.
- Silently impute, drop, or reclassify data in the statistical core without a documented, pre-registered policy.
- Choose or adjust a threshold, cost ratio, coverage margin, or comparison policy *after* inspecting the results it will be judged against.
- Proceed past Gate 1, Gate 2, or Gate 3 without a `DECISIONS.md` entry authored by the project owner.
- Introduce a new dependency (library, service, framework) without flagging it first — the dependency list in `SOFTWARE_ARCHITECTURE.md` §9 is deliberately minimal and reviewed.
- Add a database, message queue, orchestration framework, cloud service, or distributed-compute dependency (explicitly out of scope per `SOFTWARE_ARCHITECTURE.md` §10).
- Fabricate, approximate-and-present-as-exact, or "helpfully fill in" a citation, dataset statistic, author name, or paper claim. If a fact is unverified, say so — mark it `[verify]` rather than asserting it.
- Delete or overwrite anything in `data/raw/` after Phase 0, or bypass the checksum verification step.
- Force-push, rewrite history on `main`, or delete a gate tag.
- Claim an experiment is "done" or "passing" without its tests existing and green in CI.
- Weaken a baseline (e.g., under-tune the MC-dropout comparison) to make the project's own method look better.
- Represent this system as production-ready, operationally deployed, or suitable for real satellite operations decisions — it is a research artifact.

## 11. Decision Hierarchy

When guidance conflicts or a choice is unspecified, resolve in this order:

1. **An explicit `DECISIONS.md` entry** for the specific question — always wins, even over the planning documents, since it represents the most recent human decision.
2. **`PROJECT_KNOWLEDGE.md`** — goals, non-goals, requirements, assumptions.
3. **`SOFTWARE_ARCHITECTURE.md`** — structural/component boundaries and invariants.
4. **`EXPERIMENT_PLAN.md`** — what runs, in what order, with what success/failure criteria.
5. **`OPEN_QUESTIONS.md`** — if the question is listed there and unresolved, that is the signal to **stop and ask**, not to pick the "Recommended" option unilaterally and proceed. Recommendations in that document are inputs to the human decision, not pre-authorized defaults, unless a `DECISIONS.md` entry has since adopted one.
6. **This file (`CLAUDE.md`)** — behavioral rules for everything the documents above don't settle.
7. **Claude Code's own judgment** — the last resort, only for genuinely low-stakes implementation details (variable naming, minor refactors) that don't touch the statistical core, project scope, or any gated decision. When judgment is used, state the assumption explicitly in the commit message or PR description.

**The project owner (Sidh) has final authority at every level**, including overriding any of the above — but overrides happen via a logged `DECISIONS.md` entry, not silently.

## 12. Repository Conventions

- Follow the folder structure in `SOFTWARE_ARCHITECTURE.md` §3 exactly; do not introduce new top-level directories without updating that document first.
- Config-driven, not hardcoded: seeds, paths, thresholds, grids, and cost ratios live in `config/default.yaml` or `config/experiments/*.yaml` — never inline magic numbers in source files.
- Naming: modules and files use `snake_case`; experiment IDs (`E0`–`E18`) are the canonical cross-reference key used in branch names, notebook titles, config filenames, and report filenames.
- Notebooks are execution artifacts, not development scratchpads — they must run headlessly top-to-bottom (via papermill/nbconvert) in CI-like conditions. Exploratory scratch work stays local and untracked, not committed as a "notebook."
- One-command reproduction (`kc reproduce-all` or `make reproduce`) must always be kept working; treat its breakage as equivalent to a failing test suite.
- Dependency pins live in `pyproject.toml` + lockfile; no unpinned installs.
- The Dockerfile is kept in sync with the pinned environment and validated (build + `kc reproduce-all` inside the container) before any tagged release.
